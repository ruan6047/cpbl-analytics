## 1. 做了什麼（以及刻意沒做什麼）

**沒有讀 `game_livelog`。** `ML-PITCHER-SCORELESS1` 附錄 A 記載該路線七輪皆敗，共同根因
是「列的缺席偵測不到」（`pitch_cnt` 與 `main_event_no` 主序號皆非列的唯一鍵、不消耗投球
的出局事件只以列存在），而缺漏方向會讓紀錄**被高估**。本卡全程只讀官方逐場欄位
（`pitching_gamelog.runs` / `inning_pitched_cnt` / `inning_pitched_div3`）與官方逐局比分
（`game_scoreboard`）。查核可用：

```bash

```

實測命中 **2 行，兩行都在 docstring 的說明文字裡**（`scoreless_streak.py` L59「尾段完全
不讀逐打席資料」、L441 資料邊界說明），**沒有任何 import、SQL 或呼叫**。這個 grep 會有
命中是預期的——寫「應為空」會是錯的宣稱，實際要看的是命中處是不是可執行路徑。

實際做的是**把口徑抽成一個參數**：`Basis`（判準欄位 ＋ 對外名詞 ＋ 中斷原因碼）。

| 口徑 | 判準欄位 | metric | 端點 |
|---|---|---|---|
| `EARNED_RUN_BASIS`（既有，預設） | `earned_runs` | `consecutive_earned_run_free_innings` | `/api/v1/records/earned-run-free-streak` |
| `RUN_BASIS`（本卡） | `runs` | `consecutive_run_free_innings` | `/api/v1/records/run-free-streak` |

`compute_streak` 的回走邏輯、`pigeonhole_tail_outs` 的尾段下界、保留賽／季後賽／資料邊界
的處理**完全共用**，差別只有「讀哪個官方欄位」與「用哪組原因碼」。

### 1.1 9.16 的措辭（**卡面 2026-08-07 修訂版，請勿退回舊版**）

舊版寫「改做連續無失分可**完全繞開 9.16**」——**不成立**。9.16(g) 本文即為失分歸屬的
規範性條款，原文（`docs/reference/棒球規則.txt` **L6208-6211**，本次重新查證；卡面記
L6208-6210，句尾「援投手之責任」實際落在 L6211，以本次查證為準）：

> （g）在同一局中更換投手，在後援投手上場後壘上原有之跑壘員得分，或利用野手選擇使前任
> 投手遺留的跑壘員出局，因此進壘而得分者，該失分（**無論自責分或非自責分**）皆不為
> 後援投手之責任。

正確的措辭是：**該歸屬已由聯盟記錄員套用於官方逐場 `runs` 欄，我方直接讀取、不重算。**
真正繞開的是 9.16 的**主觀條款**——(c)(d) 的反事實重播（「若無失誤是否仍能得分」）與
(f)「在判斷跑壘員是否因失誤而進壘有疑慮時，應對投手有利為宜」（L6206-6207，同次查證）。
失分口徑完全不碰這三條。

### 1.2 為什麼「兩段口徑一致」是真的（而現行實作不是）

現行自責分口徑的兩段各自證明不同的命題：

| 段 | 現行（自責分） | 本卡（失分） |
|---|---|---|
| 中段 | 該出賽官方 `earned_runs = 0` | 該出賽官方 `runs = 0` |
| 尾段 | 該局官方逐局**得分**為 0 | 該局官方逐局**得分**為 0 |

尾段判準本來就是**失分**口徑的證據。接在自責分中段上時，它證的是「零得分 ⇒ 零自責分」
這個**跨口徑蘊含**；接在失分中段上時，它與中段是**同一個量的兩個粒度**（出賽 vs 局）。

**必須說清楚的界線**：這不代表現行實作會高估。尾段的證明較強（連非自責分都沒有），
混用的結果仍是自責分口徑的合法下界——`ML-PITCHER-SCORELESS1` §1.5 需求方裁定即為此。
本卡改善的是**證據標準的齊一性**與**名詞與媒體用語的對應**，不是正確性。

**也不代表採計率會變好。** 見 §4。

## 5. 建議：**並列**，失分為預設呈現面（**決定權在需求方**）

### 5.1 支持並列的證據

1. **兩者確為不同紀錄**（X1：一軍 2,163 筆出賽 `runs ≠ earned_runs`），不是同一個數字的
   兩種說法；刪掉一個就是刪掉一個真的指標。
2. **自責分口徑有它自己的用途**：它與 ERA 語意一致，且**不受記錄員失誤判定影響**——
   一個守備失誤的判定不會改變它。失分口徑則會。兩個問題不同：「這位投手表現得多乾淨」
   vs 「這支球隊多久沒讓對手踏過本壘」。
3. **並列的邊際成本接近零**：同一套演算法、同一支對帳腳本、同一組 R1–R10。新增的只有
   一個 `Basis` 設定與一個端點函式；`compute_streak` 的可執行邏輯沒有分岔（判準值一律
   走 `Basis.charged()`）。
4. **失分口徑的值恆 ≤ 自責分口徑**（X3 逐人驗證），所以並列不會出現「兩個數字互相打臉」
   的情形，只會是「較嚴格的那個 ≤ 較寬鬆的那個」，可直接用一句話解釋給讀者。

### 5.2 支持失分作為**預設呈現面**的證據

1. **名詞對得上讀者手上的數字**：兩筆 media 的用詞都是「無失分」。現行端點必須永遠帶著
   紅線 5 的警語說明「這不是無失分」——那個警語存在本身，就是名詞與讀者預期不一致的證據。
2. **口徑一致**：§1.2 的兩段同量論證。
3. **較保守**：X3 保證失分口徑恆 ≤，headline 數字不會比另一個口徑大。

### 5.3 反面意見（照實列，不藏）

- **並列會在站上出現兩個長得很像的數字**，讀者會問「到底哪個是紀錄」。這是真實的產品
  成本，需要文案紀律（兩支端點的 `metric_label`／`note` 已強制帶「自責」或「失分」二字，
  但前端仍需刻意設計）。
- **兩支端點目前都沒有前端消費者。** 自責分那支上線至今 `web/` 零消費者；本卡再加一支，
  等於未被消費的介面翻倍。若需求方認為呈現面遲遲不做，「取代」可以少維護一支。
- 若裁決為**取代**，建議取代的是**端點呈現面**而不是自責分能力本身：`EARNED_RUN_BASIS`
  應保留，因為 `strict_outs` ＋ R1 是零推論的稽核基準，拆掉會弱化對帳。

### 5.4 本卡在等裁決期間做的保守選擇

新增的兩個揭露欄位（`basis_field`、`lower_bound_note`）**只掛在失分口徑的 payload 上**。
理由：卡面驗證明文「既有 earned-run-free-streak 端點行為不得改變」，**加一個 key 也是改變**。
`tests/test_scoreless_streak_api.py::test_earned_run_payload_shape_is_frozen` 用凍結的
key 集合把這條紅線變成可執行斷言（兩個方向都驗：不得少 key、也不得多 key）。
裁決之後要不要回填，連同那份清單一起改。

**既有端點未變的證據（可重跑，非宣稱）**：以 `origin/main` = `4255426` 另開 detached
worktree，兩邊各自輸出 `streak_payload(2026,'A',limit=100)`、`(2026,'D',limit=100)` 與
單人查詢的 JSON，`diff` **完全相同**：

## 6. 誠實揭露：下界限制**不因改用失分口徑而消失**

**中途登板／中途退場、且該場後段仍有得分時，該場仍只能給鴿籠下界（多半為 0）。**
成因是官方逐場只記整場的量、不記事件時點，**與判準用 ER 還是 R 無關**。

實測（`RECONCILE.txt`，尾段查詢＝分母）：
