- 前置：[`ML-PITCHER-SCORELESS1_RESULTS.md`](ML-PITCHER-SCORELESS1_RESULTS.md)（七輪失敗模式，本卡最主要的輸入）
- 口徑單一來源：`src/cpbl/models/scoreless_streak.py` 的模組 docstring 與 `pigeonhole_tail_outs`／`last_pitch_inning` 的 docstring
- 對帳腳本：`scripts/reconcile_scoreless_streak.py`（本檔所有對帳數字由它產生）

## 0. 一句話

尾段原本只有一條下界（視窗開到比賽末端），本卡加上**第二條獨立下界**——用「官方投球數
耗盡的局」把視窗提早收掉——兩條都成立故取大者。一軍尾段採計 **24 → 29 場、126 → 156 outs**，
二軍 **19 → 22 場、152 → 167 outs**；坎南 30.0 與黃子鵬 33.2 皆不變，8 位投手的值上升、
**沒有任何一位下降**。

## 1. 前置查證：卡面點名的那條路本輪不能走

卡面把「找具備逐投手／逐局粒度的官方來源」（`stats.cpbl.com.tw` 單場 API）列為最值得先查
的一條。**本輪對官網發出任何請求都被禁止**（TrackMan 逐球爬蟲的 14 天觀測窗進行中，約 8/7
結束），所以這條**完全沒有查證**，連探查都沒做。它仍然是最有機會讓問題直接消失的方向，
建議 8/7 觀測窗結束後另卡處理。

本卡因此把範圍限縮在**現有本機資料**能不能證出更緊的下界——結論是可以，見下。

## 2. 方法：第二條下界

### 2.1 原本卡在哪裡

原式令 `n_prefix` ＝**全場**最後一個有得分的局，採計 `官方出局數 − 3 × n_prefix`。視窗一律
開到比賽末端，所以只要投手退場後對手還有得分，`n_prefix` 就被推到很後面而下界歸零。
一軍 343 次尾段查詢有 319 次卡在這裡。

### 2.2 新增的量：`last_pitch_inning()`

`cpbl.game_livelog.pitch_cnt` 是「該投手該場**累計**投球數」，`pitching_gamelog.pitch_cnt`
是官方的同一個量。累計量隨時間單調不減，於是：

> **只要在第 i 局觀測到累計值已達官方總數，該投手在第 i 局之後就不可能再投出任何一球**
> ——因為之後的球累計值會超過官方總數。

### 2.3 下界本身

令 `S` ＝ 對手打擊的總局數、`m` ＝**不晚於 `last_pitch`** 的最後一個得分局（沒有則 0）：

```
他在第 1..m 局的出局數            ≤ 3 × m                  （每半局至多 3 個出局）
他在第 last_pitch+1..S 局的出局數 ≤ 3 × (S − last_pitch)   （同上）
⇒ 他在第 m+1..last_pitch 局的出局數 ≥ 官方總出局數 − 3m − 3(S − last_pitch)
```

第 `m+1..last_pitch` 局依 `m` 的定義**全部零得分** ⇒ 零失分 ⇒ 零自責分。
`last_pitch = S`（沒有認證）時本式**退化成原式**，故取兩者最大值後既有輸出不會變小。

### 2.4 為什麼採計的出局在「他最後一次自責失分之後」

這是本卡唯一新增的實質論證，也是最該被挑戰的一段：

自責分只會記在**他讓跑者上壘的那一局**（跑者不跨局）。而讓跑者上壘一定要投球——安打／
四壞／觸身／被打出去的失誤／不死三振／捕手妨礙**都需要一顆球**。唯一不需要投球就出現
的跑者是延長賽的指定跑者，而規則 **7.01(b)(2)(C)** 明文：

> 為符合規則 9.16 自責分的計算，每半局開始位於二壘的跑壘員，**視為守備失誤上壘**

＝**非自責**，不會記到任何投手的自責分上。所以他的自責分只可能發生在第 `1..last_pitch`
局；而第 `m+1..last_pitch` 局零得分，故他最後一次自責失分必在第 `m` 局或更早。∎

（依卡面要求，這條以規則為前提的推論**先查了倉裡的 `docs/reference/棒球規則.txt` 全文**，
不是憑印象。）

## 3. 為什麼滿足紅線 2（只能低估不得高估）

### 3.1 認證只用「列的存在」，從不用「列的缺席」

卡面說「共同教訓：以某個可見量設界再證明**資料完整**這條路走不通，因為列的缺席不可
偵測。可行方向必須是『不管資料完不完整，這個界都成立』。」

本認證正是這種：

| 情境 | 效果 |
|---|---|
| livelog 完整 | 觀測到累計值達官方總數 → 認證某一局 → 下界較緊 |
| livelog 少了任意多列 | 觀測到的最大值只會**變小** → 達不到官方總數 → **不認證** → 退回原式 |

**隱藏列只能讓結論變弱，不可能讓它變強。** 這與前七輪的方向相反：前七輪是「看到 X 就
推論資料完整」，本卡是「看到 X 就推論他不可能再投球」，後者對缺列免疫。

### 3.2 逐條對照卡面「已排除的路徑」

| 已排除的路徑 | 本卡是否重走 |
|---|---|
| 以「半局是否存在」證明完整性 | **否**。不看半局存不存在 |
| 以「半局內現存列一致」推論投手獨力投完 | **否**。從不推論他在某半局拿了幾個出局 |
| 以整場出局數總和對帳 | **否**。不用任何「其他投手」的項 |
| 以 `pitch_cnt` 逐球序號閉合證明事件完整 | **否**——關鍵區別見下 |
| 以「投手換下後不得再入賽」推導下界 | **否**。不假設任何再入賽限制 |
| 以 `main_event_no` 序號密度證明無缺列 | **否**。不看序號密度 |

**與 iteration 4 的 `pitch_cnt` 用法差在哪**：那一輪要求「每位投手的 livelog 逐球序號集合
恰為 `{1..官方投球數}`」，被「`pitch_cnt` 不是列的唯一鍵（全庫 68,372 組重複）、刪掉共槽
的列不留痕跡」打穿。**本卡不數列、不要求序號閉合、不要求每個序號只出現一次**，只取
**每局的最大值**再問「哪一局起累計值已達官方總數」——重複列不改變最大值，缺列只會讓最
大值變小。iteration 4 的推翻理由對本用法不成立。

### 3.3 沒有引進新的前提

- 「每半局至多 3 個出局」——**原式就已經在用**的同一個前提。
- 「官方 `pitch_cnt` 是權威」——與既有的「官方 `earned_runs`／局數是權威」同一層級。
- 規則 7.01(b)(2)(C)——查過全文原文，用來排除唯一的無投球上壘路徑。

### 3.4 刻意不做的收緊（誠實揭露）

第 `last_pitch+1..S` 局其實**不太可能**有他的出局：他沒再投球，只剩牽制／促請裁決這類不
消耗投球的出局。規則 5.10(g) 的【加註】把後援投手綁在「投球至第 1 位擊球員出局或上壘，
或結束該局」，照這條可以把每局罰則從 **3 收到 1**，數字會好看很多（黃子鵬那場會從 2.0
變 4.0 局）。

**沒有這樣做**：那需要一串以規則為前提的推論（含傷退例外，且規則明文允許「牽制跑壘員
出局完成該局比賽則該投手允許被替換」＝真的存在 0 投球拿出局的合法路徑），而 iteration 6
正是栽在自創規則上。**這條收緊留給需求方裁定，不在本卡自行採用。**

本卡對對帳腳本的變更：

- **新增 R11**：退場局認證的獨立重算。另取 livelog 每局 `max(pitch_cnt)` 與 **NULL 計數**、
  官方 `pitching_gamelog.pitch_cnt`，以**獨立重寫**的 `_audit_last_pitch()`（刻意不 import
  runtime 的 `last_pitch_inning`）重算，驗其與 runtime 宣稱值**完全相等**。該函式對 NULL 的

- **R10 一般化**：兩條下界都獨立重算、取大者再比對，而不是只重算原式。

  之後全部」——在新下界下視窗不一定開到比賽末端（其後的局可能有得分，那些分不是他的
  責任），沿用舊寫法會誤報。

## 7. 測試與變異檢驗

新增測試測的是**行為**，不是原始碼長什麼樣（前置卡 iteration 11 的教訓）。含一組
**窮舉式保守性檢驗**：把每半局 0~3 個出局的所有配置列舉出來（6 局 × 5 種官方出局數 ×
7 種退場局 × 6 種逐局比分），逐一驗「採計值 ≤ 該可行世界視窗內的真實出局數」。

**變異檢驗**（注入本該被抓到的缺陷，證明測試真的紅）：

## 8. 量測過但**沒有採用**的方案（依卡面紅線 2 分開呈現）

有一條能把數字拉高很多的路，我實作到可量測的程度後**決定不出貨**，理由如下。

### 8.1 方案內容

以 canonical PA 表（`cpbl.game_plate_appearances`）證明「某半局的某個出局是**別的投手**
記下的」：一筆 `outcome_family ∈ (out, sacrifice)` 的 PA，其 `start_pitcher_acnt` 與
`end_pitcher_acnt` 都不是本投手 ⇒ 該出局屬於別人。用它縮小前後兩段的容量。

### 8.2 量測到的效果

| 方案 | 一軍採計 | 二軍採計 |
|---|---|---|
| 基線 | 24 場 / 126 outs | 19 場 / 152 outs |
| **本卡出貨的** | 29 場 / 156 outs | 22 場 / 167 outs |
| 加上 PA 出局歸屬 | **46 場 / 248 outs** | **66 場 / 379 outs** |

### 8.3 為什麼不出貨

這個方案的證明前提是「每一筆被標成出局的 PA 都真的記下了至少一個出局，且不同 PA 對應
不同的出局」。**這個前提在現有資料上被證偽**：全庫有 **134 個半局**含 **4 筆以上**
`out/sacrifice` 族的 PA——一個半局不可能有 4 個出局。抽驗三例（`2018/A/116` 半局 2 第 7 局
出現 界外飛球接殺／刺殺／三振／三振 四筆、打者各不相同）確認是**真實的資料瑕疵**，
不是我的解讀錯誤。

我可以加守衛（半局出局 PA > 3 即不認證、`pre_state.outs` 槽重複即不認證），實測能擋掉
全部 134 個已觀測案例。但**擋得掉已觀測的案例，不等於擋得掉所有案例**：只要某個半局有
一筆假的出局 PA、同時有一個真的非 PA 出局（盜壘刺／牽制），總數仍是 3、守衛看不出來，
而那正好是高估路徑。要主張守衛完備就得宣稱「已窮舉所有瑕疵型態」——那是機率論證，
卡面紅線 2 明令不可以拿它替代證明。

**所以：可證的部分（第 2 節）出貨，這一段不出貨。** 若需求方願意接受「標示為啟發式、
與可證部分分開呈現」的形式，程式上是小改動，但那需要需求方明示。

### 8.4 附帶發現：PA 表的兩個資料問題

1. **134 個半局的出局 PA 超過 3 筆**（上述）——這是獨立於本卡的資料正確性問題。
2. **`pre_state.outs` 有時未遞增**：1,174 組 `(半局, 出局數槽)` 出現多筆出局 PA
   （例 `2018/A/78` 第 4 局四筆 PA 的 `pre_outs` 全是 0）。
3. PA 表比 livelog **落後 4 場**（`2026/A/223~225`、`2026/D/51`；最後 build 時間
   2026-07-26 12:38 UTC）——這只是每日 build 的時間差，不是缺陷，但也代表 8.1 方案對最新
   場次天生失效。本卡出貨的方法**不依賴 PA 表**，所以不受影響（黃子鵬 2026-07-26 照樣算得出來）。

## 9. 我認為最可能被反例打穿的地方（主動揭露）

依卡面「主動指出自己的弱點比被抓到有價值」，按風險排序：

1. **「讓跑者上壘一定要投球」這條全稱命題**（§2.4）。我列舉了安打／四壞／觸身／失誤／
   不死三振／捕手妨礙／延長賽指定跑者，並用規則 7.01(b)(2)(C) 把最後一項排除。
   **如果存在第八種我沒想到的上壘方式，且它不需要投球、又算自責**，這條下界就破。
   建議查核者直接針對這句構造反例——這是本卡最單薄的一環，因為它是**列舉**而不是推導。
2. **`game_livelog.pitch_cnt` ＝ 累計投球數**這個語意。我沿用前置卡 §A.c 的既有結論
   （該卡以它與官方 `pitch_cnt` 互為同一量），並實測全庫 39,917 組 (場次, 投手) 中
   39,684 組 livelog 最大值恰等於官方值。但 **231 組 livelog 最大值 > 官方值**、2 組 <。
   前者會被守衛擋下（不認證），後者本來就達不到總數。若這個欄位在某些年份語意不同
   （例如曾是「該打席球數」），認證會系統性出錯。
3. **`is_change_player` 列帶著前任投手的累計投球數出現在下一局**（實例 `2026/A/223`）。
   我用「取最早達成官方總數的局」規避，不判讀該旗標。若存在**反向**樣態——某列帶著
   **偏大**的 `pitch_cnt` 出現在**偏早**的局——就會把退場局認證得太早而高估。
   我沒有窮舉證明這種樣態不存在，只有「觀測最大值 > 官方總數即不認證」這道守衛擋著
   最極端的形式。
4. **`S` 取自 `max(scoreboard 局序)`**。若記分板有「超出實際比賽範圍的空白列」
   （前置卡 §A.0 提到 2018+ 有 11 個），`S` 會偏大 → `3 × (S − last_pitch)` 罰則偏大 →
   **偏保守**，方向安全。但若反過來記分板**少**了尾端的局，`S` 偏小、罰則偏小 → 高估。
   逐局比分完整性閘門（總和 ＝ 官方終場得分）只在缺的那局有得分時才會攔下。
5. **8.3 節的守衛完備性**——我已主動不出貨，但若查核者認為 §2 的方法也有類似的
   「已觀測案例都擋得住 ≠ 所有案例都擋得住」問題，那是有效的挑戰方向。
