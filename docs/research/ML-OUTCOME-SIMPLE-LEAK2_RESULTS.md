## §3 為什麼是 (a)：固定區間量的不是校準

### 3.1 斜率的抽樣變異與辨別力反向連動

校準斜率是再校準回歸 `y ~ sigmoid(a + b·logit(p̂))` 的 `b`。其 Fisher 資訊
∝ `n · Var(logit p̂) · p(1−p)`，故 **`Var(b̂)` 與預測的 logit 離散度成反比**。
模型愈弱、機率愈往基準率壓縮，同一個「完美校準」的模型量到的斜率就愈飄。

| | logit(p̂) 標準差 | 斜率點估計 |
|---|---:|---:|
| 洩漏模型 | 0.5592 | 1.0547 |
| 誠實模型 | 0.2064 | 1.3732 |

### 3.2 零假設模擬：固定區間在誠實模型下的偽失敗率 42%

固定 `p̂`、重抽 `y ~ Bernoulli(p̂)`（即**假設模型完美校準**）、重解斜率，2,000 次：

| | 零假設下斜率 95% 區間 | `[0.8, 1.2]` 的偽失敗率 |
|---|---|---:|
| 洩漏模型（由 reliability decile 近似還原 p̂） | **[0.787, 1.229]** | **7.9%** |
| 誠實模型（本次重訓實際 p̂） | **[0.559, 1.489]** | **41.8%** |

兩件事同時成立：

1. **舊門檻與洩漏模型的零假設區間高度吻合**——`[0.8, 1.2]` 與 `[0.787, 1.229]` 兩端相差
   都在 0.03 以內。**這只是數值上的吻合，不足以證明它當初就是照著這個模型訂的**（無歷史
   紀錄可查證）。可驗證的部分是下一條：同一個固定區間換一個模型就完全失效。
2. **同一個區間套到誠實模型上，會誤判 41.8% 的完美校準模型為失敗**。一個型一誤差 42%
   的檢定不是閘門，是雜訊產生器。

觀測到的 1.3732 在誠實模型的零分布下雙尾 **p = 0.122**，未達 5% 顯著；
非參數行事曆週區塊 bootstrap 的斜率 95% 區間 **[0.885, 1.875]** 同樣涵蓋 1.0。
**沒有證據說這個模型失準。**

> **條件零假設**：模擬假設「給定 p̂，各場賽果彼此獨立」。同週賽果若有殘餘相依，效果的
> **方向取決於相依的正負**：**正向**群聚會讓真實零分布變寬，這裡較窄的 IID 區間會使實際
> 型一誤差**高於**名目 5%；**負向**相依則相反，零分布較窄、IID 區間偏寬、型一誤差低於
> 名目值。**本卡未估計該相依的方向與大小**，因此不主張這個檢定往哪一邊偏保守。
> 下文所有「5%」皆指此條件下的名目值。

**診斷（不是上述區間的驗證）**：同一批 1,585 筆 OOS 預測，把再校準回歸
`y ~ sigmoid(a + b·logit p̂)` 的斜率估計量算 sandwich SE，cluster 取 `(season, ISO week)`
共 149 個行事曆週，未套小樣本修正：

| 斜率估計量的 SE | 值 |
|---|---:|
| IID（`H⁻¹` 對角） | 0.250849 |
| 行事曆週 cluster-robust | 0.249491 |
| 比值（cluster ÷ IID） | **0.9946** |

取得方式（唯讀，不寫 DB／artifact）：

```bash
uv run python scripts/outcome_simple_calibration_audit.py out.json   # 讀 out.json 的 slope_se_week_cluster_vs_iid
```

這是**觀測資料上的診斷**，與上表的 H0 參數 bootstrap 是不同物件：後者問「若模型完美校準，
斜率會怎麼飄」（重抽 `y ~ Bernoulli(p̂)`），前者問「就這批資料而言，允許同週殘差相關後
估計量的變異會不會變大」。因此它只支持一句話——**無證據顯示週內群聚在此資料上放大了
變異**（cluster SE 略小於 IID）。它**不能**反過來當成 H0 區間正確的證明，也不排除其他
相依結構。iteration 5 查核者以同一批預測獨立量到 IID `0.250856`／週 cluster `0.250431`
（比值 0.9983），與此處結論一致；數值小差來自 cluster 界定與小樣本修正的取捨不同。

### 3.3 用能反映校準的指標看，誠實模型反而更準

斜率是唯一惡化的校準統計量，而它正是雜訊最大的那一個：

| 校準指標 | 洩漏版 | 誠實版 | 方向 |
|---|---:|---:|---|
| ECE（十分位加權絕對偏差） | 0.0290 | **0.0173** | 改善 |
| \|校準截距\| | 0.0637 | **0.0426** | 改善 |
| 校準斜率 | 1.0547 | 1.3732 | 惡化（但 p = 0.122，不顯著） |

「模型講 60% 的那些場，實際上真的贏約 60% 嗎」——這個問題由 ECE 與截距回答，兩者都變好了。

### 3.4 新門檻不是「調到剛好讓它過」

| | 舊門檻 | 新門檻 |
|---|---|---|
| 形式 | 固定 `[0.8, 1.2]` | 該次回測零假設分布的 95% 區間 |
| 型一誤差 | 隨模型辨別力漂移（7.9% → 41.8%） | 條件零假設下名目 5%（見 §3.2 註） |
| 套在洩漏模型上 | `[0.8, 1.2]` | `[0.787, 1.229]`，**兩端各略寬約 0.02** |
| 套在誠實模型上 | `[0.8, 1.2]` | `[0.559, 1.489]` |
| 模型變強時 | 不變 | **自動收緊** |

新規則是舊門檻的推廣：在洩漏模型的辨別力水準上，兩者幾乎重合（新界線略寬約 0.02，
不是更嚴，也談不上實質放寬）。實質變寬只發生在誠實模型那一端，而那一段寬度正是
統計上無從分辨的範圍——不在「模型可能真的失準」的範圍內放寬：本次若斜率是 1.6 仍會
FAIL（超出 1.489）。判準在看到結果之前就由原則決定，不含任何依觀測值挑選的自由度。

## §4 為什麼不是 (b) 溫度縮放，也不是 (c) 下架

### (b) 後處理：時間外驗證證明無效

以「該測試季之前所有測試季的 OOS 預測」擬合溫度、套用到當季（嚴格時間外，不 in-sample）：

| | 原始 | 溫度縮放後 | Δ |
|---|---:|---:|---:|
| Brier（2022–2025 評估區） | 0.244767 | 0.244709 | −0.000058 |
| LogLoss（2022–2025 評估區） | 0.682618 | 0.682506 | −0.000113 |
| 準確率 | 0.55836 | 0.55836 | ±0 |
| 斜率 | 1.3732 | 1.1060 | −0.267 |

改善量在小數點後第四位以下，且逐年擬合出的溫度在 1.09–1.46 之間跳動——這是擬合雜訊的
特徵，不是穩定的系統性偏差。**為了修一個統計上不存在的偏差，換來一個新的、不穩定的
擬合面與 serving 複雜度，不划算。** 與 GAME-RECAP-WP-CAL1 的事後校準 No-Go 判定同調。

### (c) 下架：模型確實有可證明的（小）預測力

Brier 與 LogLoss 對全押主場的配對區塊 bootstrap 95% 區間全負，4/5 個測試季勝出。
優勢很小（準確率 +3.0pt、Brier −0.0044），但**是真的**。誠實的處置是繼續提供並如實
標示幅度，不是因為數字不好看就下架——後者跟當初用洩漏數字包裝一樣不誠實，只是反向。

## §5 交叉檢查：2018 世代分裂不是斜率的成因

LEAK1 查核者的 Informational finding：2018 前無 `pitching_gamelog`，三個 starter 欄退化為
「純上季值」，2018+ 才是真 as-of running state；訓練池 9,185 列中約 7,000 列屬前者。
兩者皆 leakage-free，但語意不同。是否為斜率被推高的成因？

限制訓練池為 2018+（語意同質）重跑同一條走查（測試期 2021–2025 本來就全在 2018 後）：

| 訓練池 | n | 準確率 | Brier | LogLoss | ECE | 斜率 | 零假設 95% 區間 | p |
|---|---:|---:|---:|---:|---:|---:|---|---:|
| 全史（現行） | 9,185 | **0.5584** | **0.24496** | **0.68300** | **0.0173** | 1.3732 | [0.559, 1.489] | 0.122 |
| 僅 2018+ | 2,298 | 0.5363 | 0.24742 | 0.68802 | 0.0228 | 0.8890 | [0.549, 1.487] | 0.639 |

三個結論：

1. **不是成因**：兩者的 logit 離散度幾乎相同（0.206 vs 0.210），零假設區間幾乎重合。
   壓縮來自訊號本身弱，不是世代混合。
2. **斜率在兩個設定間擺盪 0.48，而零假設區間寬度約 0.94** ——同一個統計量在兩個都合理的
   設定下的擺幅遠小於它的雜訊底線。這是「斜率點估計不可作為判準」的直接演示。
3. **若真的照斜率點估計挑模型，會挑到比較差的那個**：2018+ 版斜率更接近 1，但準確率、
   Brier、LogLoss、ECE **四項全部變差**。這正是舊門檻的失效模式。

依卡面邊界，本卡不改訓練母體。世代語意分裂若要處理屬另一張卡。

## §6 落地狀態一致性

| 項目 | 狀態 |
|---|---|
| `model_versions(task='outcome_simple')` | `outcome-simple-1785117621`，含 `gate.deployable = true` 與 `calibration_null` 全部依據 |
| serving artifact `outcome_simple.joblib` | 同一次執行寫出，內含 `version = outcome-simple-1785117621` 與 `gate` |
| 兩者關係 | **一致**（同一次 `cpbl-train-outcome-simple` 產出），無半套狀態 |

閘門失敗路徑（本次未觸發）也不再靜默，且**成因判別在後端做一次**：`pregame_serving.py`
比對 artifact 自陳的 `version` 與 `model_versions` 最新列，回傳 `status` 加一個
`degradation` 判別碼——

| `degradation` | 成立條件 | 介面可以說什麼 |
|---|---|---|
| `gate_failed` | DB 記下 `deployable=false` | **唯一**能講「最新回測未通過部署閘門」 |
| `version_unknown` | serving artifact 無 `version` 欄（去洩漏前的舊格式） | 只能說無法確認是否為最新產出 |
| `backtest_unknown` | 回測那一側讀不到（DB 例外／無紀錄／`gate` 欄缺席） | 只能說閘門結果無從確認，不得猜通過與否 |
| `version_mismatch` | 兩側都讀到、回測 `deployable=true` 但版本不一致 | 可附註該次回測本身已通過閘門 |

判別順序（`gate_failed` → `version_unknown` → `backtest_unknown` → `version_mismatch`）與
理由寫在 `serving_state()` 的 docstring。三個渲染賽前勝率的介面——首頁 `DailyHub`、
`/methodology#pregame`、賽況頁 `games/[sno]` 的 `PregameCard`——共用同一支
`pregameServingNotice()` 映射文案，且各自從**產生該畫面機率的那一份 response** 取狀態
（單一來源不變式）。前端對「該次回測已通過閘門」這句話另要求 `backtest_deployable === true`，
不靠後端保證；未知判別碼一律落到不含閘門宣稱的中性文案。訓練 log 亦明講「serving 仍為
哪一版、對不上哪一版回測」。
