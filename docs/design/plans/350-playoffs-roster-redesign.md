## 1. 資料可得性查證（先於設計）

**限制**：Issue body 規定不改 API 與 DB；驗收 3 要求「沿用現有名單資料來源」。

| 需要的資料 | 現有名單 API（`/api/v1/playoffs/roster`）有沒有 | 其他現有 API | 結論 |
|---|---|---|---|
| 兩隊、球員、官方守位大類（投／捕／內／外） | 有：`teams[].members[].official_position` | — | 可用 |
| 投手角色 | 有：`tactical_roles`，v2 格式 | — | 可用 |
| 個人 G、成績一行 | 有：`background.g`、`background.line`（`era`、`ip`、`avg`、`ops`…）、`series.g`、`series.line` | — | 可用 |
| **細守位**（一壘、游擊、左外…）與**各守位出賽數** | **沒有**。`official_position` 只到「內野手／外野手」 | `GET /api/v1/season/fielding`：`items[].{player_id,pos,g}`，2026 一軍例行賽。實測 515 列、約 72KB，前端已有 `web/src/lib/api.ts:644` 的呼叫函式 | 不改 API 也拿得到，但要新增第二個資料來源。它不帶名單的 `context_version`，有混用不同版本資料的風險（PRD v2 第 3 區要求「不能混版」）。只有例行賽，沒有本系列的分守位資料 |
| **DH 先發場數（本系列）** | **沒有** | `GET /api/v1/games/{sno}/live`：`batting[].role_type`（只有 先發／非先發）加 `livelog[].defend_station_code`（實測有 `DH`、`PH`…）。示意以「先發者本場第一個打席的 `defend_station_code`」推算 | 不改 API 能推，但每場 payload 實測 276–635KB，最多 7 場。而且推算方式未驗證是否等同官方的先發守位。**不建議由前端推算** |
| **DH 先發場數（例行賽）** | **沒有** | 沒有任何現成 API 提供。`rows.py` 的 `_primary_positions` 用「打擊出賽 − 守備出賽」推算 DH，算的是出賽不是先發；實測對 10/34 名野手算出負值（以本快照的名單 `background.g` 減 `/season/fielding` 非投手守位出賽合計驗算）（一場守多位會重複計），不可用 | **需改 API，超出本卡限制** |

**結論**

1. 修訂方案的**投手部分**只需要名單 API，做得到。
2. **野手依守位分區**：
   - 不改 API 的做法是前端多呼叫一支 `/season/fielding`。這和驗收 3「沿用現有名單資料來源」的字面衝突，需求方要決定接不接受（Q6）。
   - 乾淨的做法是在名單 API 加欄位，但**需改 API，超出本卡限制**。
3. **照需求方原話的 DH 規則（DH 先發超過 N 場）**：
   - 例行賽範圍：**需改 API，超出本卡限制**。
   - 本系列範圍：只能由前端逐場抓 `/games/live` 來推算。我不建議這樣做，同樣歸入 Q6。
4. **DH 規則和 #349 的關係**：
   - DH 區是名單的**呈現分組**，資料來自比賽紀錄，不讀也不寫 `tactical_roles`，**不碰 #349 的角色判定規則**。
   - 但角色詞彙裡本來就有「指定打擊」角色（`canonical.py` `FIELDER_ROLES_V2`）。若需求方的意思是「DH 先發超過 N 場就把**角色標籤**改成指定打擊」，那就是角色規則，屬 #349／#316 的範圍，不屬本卡。此點列入 Q4 的說明。

## 2. 修訂方案 C：兩隊並列「位置區塊」表（唯一方案）

**示意截圖**

| 截圖 | 檔案 |
|---|---|
| 桌機 1280，投手段 | `350-assets/mockup-c-desktop-1280-pitchers.jpg` |
| 桌機 1280，野手段 | `350-assets/mockup-c-desktop-1280-fielders.jpg` |
| 390，投手段 | `350-assets/mockup-c-mobile-390-pitchers.jpg` |
| 390，野手段 | `350-assets/mockup-c-mobile-390-fielders.jpg` |
| 示意頁 | `350-assets/mockup-c.html` |

**結構**：A 的兩隊並列，加上 B 的數值。每個區塊回答「這個位置兩隊各有誰、各自的數字是多少」。

1. **頂部組成列**：兩隊各一行，「投手 15 · 捕手 3 · 內野 8 · 外野 6」。
2. **投手段：依角色分區**。投手沒有細守位，角色就是投手的「位置」。
   - 區塊順序：先發 → 長中繼 → 中繼 → 勝利組 → 拆彈組 → 終結。
   - 區塊標題附兩隊人數，例如「先發 6 · 5」。
   - 區塊內左右兩欄是兩隊的小表：人名｜出賽｜ERA｜局數。390 寬時藏起局數。
   - 依出賽數由多到少排。
3. **野手段：依守位分區**。
   - 區塊順序：捕手 → 一壘 → 二壘 → 三壘 → 游擊 → 左外 → 中外 → 右外 → 指定打擊。
   - 區塊內是兩隊小表：人名｜該守位例行賽出賽｜OPS｜AVG。390 寬時藏起 AVG。
   - 依該守位出賽數由多到少排，所以每區第一列就是該隊在這個守位最常上場的人。
   - 守過多個守位的人，會在各守位出現，數字是他在該守位的出賽數（Q2）。
4. **DH 區塊**：依 Q4、Q5 的結果決定誰能進。示意暫以「本系列 DH 先發 ≥1 場」列出，並在區塊上標明門檻待定：味全劉俊緯 2 場、張祐銘 1 場，兄弟王威晨 3 場。
5. **其他維持現狀**：資料範圍切換（例行賽背景／本系列實戰）、能力與走勢抽屜、ⓘ 說明，都沿用現有。
6. **主視圖拿掉的內容**：PR 標籤、近 15 場箭頭、球隊／守位篩選與排序。要不要放進預設收合的「球員明細」，見衝突 2。

**390 寬**
- 仍是兩隊左右並列。
- 實測 `scrollWidth＝390`，沒有人名被截斷。
- 整區約 2,511px 高；現況只看一隊就是 4,759px。

**桌機 1280**
- 區塊兩兩並排，每個區塊內都帶隊徽與隊名欄頭，避免左右欄看錯隊。
- 整區約 1,560px 高；現況兩隊全開是 3,118px。

**已知缺點**
- 同一投手有多個角色時會重複出現。例如兄弟呂彥青出現在勝利組、拆彈組、終結三區。需求方沒有針對這點裁示，沿用「角色平列不分主次」。
- 野手依「守過的每個守位」列出時，會有只守過 1 場的雜訊列，例如姚冠瑋列在捕手區、出賽 1G。要不要過濾見 Q2；規劃者不自訂門檻數字。

## 3. 待需求方確認（每題最多兩個選項，附建議）

**Q1「列首位」的意思**
- 甲：「守位」的同音字，野手依守位分區（mockup C 的做法）。**建議甲**。原話後半句是「只列主力好像看不出什麼」，指的是角色分區看不出誰守哪裡。
- 乙：字面的「首位」，每區只列最常上場的第一人。

**Q2 野手放在哪些守位**
- 甲：守過的每個守位都列，數字是該守位出賽數，像深度表。**建議甲**，因為工具人的價值正好在這裡看得到。
- 乙：只放在主守位（出賽最多的那個），每人只出現一次。

**Q3「該位置的數值」**
- 甲：區塊標題放兩隊人數；個人列放投手的「出賽、ERA、局數」，野手的「該守位出賽、OPS、AVG」（mockup C 的做法）。**建議甲**。
- 乙：甲之外，區塊標題再加區塊合計，投手區算 ERA、野手區算 OPS。野手會在多個守位重複出現，合計的意義較弱。

**Q4 DH 先發場數的計算範圍**
- 甲：本系列（隨系列進行累積），和例子「台灣大賽」一致。
- 乙：例行賽。目前沒有任何 API 提供，需改 API。
- **建議甲**。注意：這是名單分組，不改「指定打擊」角色標籤；若要改角色標籤，屬於 #349／#316 的範圍。

**Q5 門檻**
- 甲：「三場以上」（≥3）。
- 乙：照字面「超過三場」（>3）。
- 事實：本系列已打 3 場，照乙目前沒有人會進 DH 區，例子裡的劉俊緯（2 場）照甲也進不去。
- **建議交需求方直接給數字或比例**，規劃者不自訂。

**Q6 資料取得方式**（決定本卡能不能照原話做）
- 甲：回到需求階段，授權擴充名單 API，每名野手加上「各守位出賽數」與「DH 先發數」（本系列＋例行賽），跟名單同一個 `context_version`。**建議甲**，理由是單一來源、不混版、不需逐場抓 0.3–0.6MB 的賽況。
- 乙：不改 API。守位改用既有的 `/season/fielding`，接受第二個資料來源；DH 區改用既有的「指定打擊」角色。這和原話的 DH 規則不同，而且 `/season/fielding` 只有例行賽。

## 5. 實作計畫（等 Q1–Q6 定案後才定稿，先列骨架）

這份是**預估**，執行者可以調整相鄰檔案。

**若 Q6＝甲（擴充 API）**：本卡需求要退回需求階段改寫「不改 API」的限制，或另開 API 卡作為前置。規劃者不自行擴大範圍，前端部分沿用以下骨架。

1. **`web/src/lib/playoffs-roster.ts`**
   - `PITCHER_ROLE_ORDER`、`FIELD_POS_ORDER`
   - `pitcherBlocks(teams, scope)`
   - `fielderBlocks(teams, posG, dhStarts, threshold)`：純函式；同出賽數依 `player_id` 排序；空區省略。
   - 未知角色或守位接在尾端。
2. **`web/src/components/playoffs/roster-section.tsx`**
   - 新增無 hooks 的 `RosterBlocks`（兩隊小表）。
   - 資料範圍 state 放在 `RosterBody`。
   - 是否保留「球員明細」依衝突 2 的裁定。
   - 抽屜焦點歸還：同一球員會有多個觸發點，要記住實際觸發的元素，不能只用 `data-open-player` 的第一個。
3. **`playoffs-live.tsx`**：預期不改。
4. **測試**：用 `npm test`，也就是 `node --test` 加 `react-dom/server` 靜態渲染，不是 vitest。要涵蓋：
   - 兩隊欄同時存在
   - 區塊順序
   - 多守位與多角色重複列出
   - 依出賽數降冪
   - DH 門檻的邊界（等於門檻、門檻減一）
   - 缺名單時該隊「待更新」
   - `memberRoles` 對 v2 角色空值仍拋錯
   - 既有小卡相關測試，若保留明細則照舊通過
5. **驗收取證**（不變）：真實瀏覽器從正式站導覽列點擊進入 `/playoffs` →「系列賽名單」→ 截圖 → 重新載入 → 截圖。桌機 1280 與 390 各一組。

**回復、停止條件、驗收外檢查、審核外傳**：同前版。
- 回復：`git revert` merge commit，再由主站 bump submodule。
- 停止條件：需要改 API／DB／角色規則時停下回報。
- 驗收外檢查（ruff、pytest、`cpbl-train`、`build:check`）交需求方保留或排除。
