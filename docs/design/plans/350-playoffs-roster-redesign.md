## 1. 現況：哪裡難讀（以正式站畫面為證據）

取證方式：真實瀏覽器（Claude Browser）開 https://cpbl.ruan-ruan.com/playoffs ，點一級頁籤「系列賽名單」。當時是台灣大賽（味全 vs 兄弟），預設資料範圍為「例行賽與對戰背景」。

| 截圖 | 檔案 |
|---|---|
| 桌機 1280 寬 | `350-assets/current-desktop-1280.jpg` |
| 手機 390 寬 | `350-assets/current-mobile-390.jpg` |

1. **預設只有一隊，看不到對照。**
   - 球隊篩選預設選第一隊，來源是 `roster-section.tsx` 的 `RosterBody` `useState(data.teams[0])`，畫面上只出現「味全 32 人」。
   - 改點「全部」之後，兩隊上下堆疊。DOM 量測：區塊高 3,118px，兄弟的區塊起點比味全低 1,539px。
   - 結果是兩隊在任何寬度下都無法同畫面對照。
2. **沒有隊級組成摘要。**
   - 隊級資訊只有「32 人」與「投手 15／野手 17」兩個小字計數。
   - 角色分布（先發幾人、勝利組是誰、主力是誰）必須逐張小卡數。
3. **控制項比內容先佔畫面。**
   - 共 4 組分段控制、12 顆按鈕（球隊、資料範圍、守位、排序）。
   - 390 寬時這 4 組各占一列（頂端 y＝284、324、364、404），第一張小卡從 y＝502 才開始。
4. **小卡細節蓋過組成。**
   - 每張卡有姓名、守位、角色、G、一行成績、近 15 場箭頭、PR 標籤。
   - 味全 32 張卡中，17 張的箭頭顯示「— —」（樣本不足）；13 張有 PR 標籤（共 24 個），卡高因此參差。
   - 390 寬時一卡 122px、一隊 4,759px，一屏只看得到約 3 人。

結論：問題在「資訊的組織單位是單一球員」，而需求要的單位是「兩隊陣容」。只調排版解決不了，需要新增隊級對照層。

## 2. 方案

兩方案都只用現有 API 已回傳的欄位：

- `official_position`
- `role`
- `tactical_roles`／`tactical_role`（經 `memberRoles()`）
- `background.g`、`series.g`（經 `scopeG()`）
- `background.line`
- `background.level`
- `roster_status`

API／DB／角色規則都不動。

### 方案 A：陣容對照表（推薦）

**示意截圖**

| 截圖 | 檔案 |
|---|---|
| 桌機 1280 | `350-assets/mockup-a-desktop-1280.jpg` |
| 390 投手段 | `350-assets/mockup-a-mobile-390.jpg` |
| 390 野手段 | `350-assets/mockup-a-mobile-390-fielders.jpg` |
| 示意頁 | `350-assets/mockup-a.html` |

**版面結構**

- **兩隊固定並列**：左欄一隊、右欄一隊，順序照 API `teams` 陣列，不再預設只顯示一隊。
- **組成列**：每隊一條 32 格比例條，分投／捕／內／外並附人數。390 寬改成一行文字：「投 15 · 捕 3 · 內 8 · 外 6」。
- **角色對照表**：分「投手」「野手」兩段，段標附兩隊人數。
  - 每一列是一種角色，左格、右格各列出該隊擁有此角色的人數與球員名牌。
  - 名牌內容是「姓名＋（野手加守位簡寫）＋出賽 G」。G 跟著目前的資料範圍。
  - 同列名牌依 G 多到少排，所以每列最前面就是這個角色最常上場的人。這是「誰是主力」的直接答案；野手另有現成的「主力」角色列。
- **列序（隊級閱讀順序，不是個人主次）**
  - 投手：先發 → 長中繼 → 中繼 → 勝利組 → 拆彈組 → 終結，照比賽進程排。
  - 野手：主力 → 指定打擊 → 工具人 → 守備替補 → 代打 → 代跑 → 替補。
  - 兩隊都沒有的角色整列省略；不在已知清單的新角色依出現順序接在最後（容納 #349 可能補標的角色）。
- **多角色球員**：在每個所屬角色列都會出現，不宣告主次。這沿用 PRD v2 第 3 區「角色平列、無主次」與 `canonical.py` 「固定順序只供序列化，不表示主次」。
- **球員明細**：表下放一個 `<details>`「球員明細（成績・近 15 場・官方 PR）」，**預設收合**。
  - 展開後就是現有的小卡網格與球隊／守位篩選、排序，內容不變。
  - 箭頭、PR、一行成績都收進這裡，主視圖不再顯示。
- **點名牌**：開啟現有的能力與走勢抽屜，行為不變。
- **資料範圍切換**：「例行賽背景／本系列實戰」提到區塊標題右側，同時作用在對照表的 G 與明細區。

**390 寬**

- 仍是兩欄並列，每欄約 170px。中文名 2–4 字的名牌一行可放兩個。
- 角色名改成列上方的小標，橫跨兩欄。
- 實測 `scrollWidth＝390`，無橫向溢出。
- 整區高度約 1,940px（現況單一隊就 4,759px），兩隊都含在內。

**和現況的差異**

| 項目 | 現況 | 方案 A |
|---|---|---|
| 預設看到幾隊 | 1 | 2（並列） |
| 隊級組成 | 只有「32 人／投手 15／野手 17」 | 守位比例＋各角色人數與名單 |
| 主視圖控制項 | 4 組 12 鈕 | 1 組 2 鈕（資料範圍）；其餘收進明細 |
| 箭頭／PR／成績 | 每張卡常駐 | 收進明細；名牌 `title` 帶一行成績 |
| 桌機高度 | 單隊 1,603px／兩隊 3,118px | 約 942px（兩隊） |

**已知缺點（交需求方看 mockup 判斷）**

- 同一人可能出現在多列，例如兄弟呂彥青同時在勝利組、拆彈組、終結三列。
- 本輪野手「主力」與「工具人」高度重疊（味全 10 與 10），野手段因此偏長。#349 重算工具人後會減少，但不保證消失。

### 方案 B：組成摘要＋並列清單（不推薦）

**示意截圖**

| 截圖 | 檔案 |
|---|---|
| 桌機 1280 | `350-assets/mockup-b-desktop-1280.jpg` |
| 390 | `350-assets/mockup-b-mobile-390.jpg` |
| 示意頁 | `350-assets/mockup-b.html` |

**版面結構**

- **上方「陣容組成」對照表**：列是投手、各投手角色、野手、捕／內／外與各野手角色；中間兩欄是兩隊人數，兩側是背對背的長條。表下註明「角色可重複計」。
- **下方「名單」**：桌機兩隊並列兩張精簡表（球員｜角色｜出賽｜一行成績），依守位分組。
- 箭頭與 PR 拿掉，改由抽屜呈現。

**390 寬**

- 組成表維持兩隊對照。
- 名單改成一次一隊（加一個球隊分段切換），並隱藏成績欄。

**不採用的理由**

- 數字對照很清楚，但「誰是主力」要往下看名單才知道。
- 390 寬時名單又回到一次只看一隊，正是現況第 1 點的病灶。
- 它還同時引入第二種表格呈現（手刻表或 `DataTable`），版面比 A 多一層。

**推薦 A 的理由**：只有 A 能在同一個平面、桌機與 390 寬都不切換的情況下，一次回答「各幾人、角色分布、誰是主力」三件事。

**衝突與待需求方裁定（規劃確認時一併呈現）**

1. **觸控目標 44px**（§1 原則 6、§4 鐵則、§7）
   - 名牌示意高度約 26px。若每個名牌都做成 44px 高，390 寬時整區高度約增加 1.6 倍，失去「一眼」效果。

   - 選項乙：名牌改成純文字、不可點，要開抽屜一律從展開的明細小卡點。
   - 規劃者傾向甲，但這屬於設計系統例外，⛔ 不自行擇一。

   - 裁定②允許「拿掉、摺疊現有標記」，但 PRD 是較早定案的產品規格，需要需求方在規劃確認時明示本卡以摺疊方式取代。

## 4. 推薦方案 A：實作計畫

檔案與段落都是**預估**。執行者可以調整相鄰測試、共用函式與實作位置。不可做的事列在 §6。

### 4.1 預估改動

**`web/src/lib/playoffs-roster.ts`（只加純函式、常數與文案）**

- `PITCHER_ROLE_ORDER`、`FIELDER_ROLE_ORDER`：與 `src/cpbl/rosters/canonical.py` 的 `*_ROLES_V2` 同一組集合，只是改成閱讀順序。另加註「隊級閱讀順序，不表示個人主次」。
- `positionCounts(team)`：回傳 `{投手, 捕手, 內野手, 外野手}` 人數。
- `roleRows(teams, role, scope)`：回傳 `[{ role, cells: [{ team_code, members (依 scopeG 多到少，同 G 時沿用既有 byPos 次序) }] }]`。
  - 已知角色先排、未知角色依出現序接在後；兩隊皆空的列省略。
  - v1 legacy 沒有角色的人，放進最後的「未標角色」列（文字用 `ROSTER_COPY.missing` 或新文案，交執行者定）。
- `ROSTER_COPY`／`ROSTER_METHOD_HELP` 補「名牌旁為出賽數，同一人多角色會重複出現」一句。這句放進 ⓘ，不在主視圖常駐說明。

**`web/src/components/playoffs/roster-section.tsx`**

- 新增無 hooks 的 `RosterCompare({ data, scope, onOpen })`：組成列、兩段角色對照表、名牌按鈕。
- `RosterBody`：資料範圍 state 提到最上層，`RosterCompare` 與明細共用；明細外包 `<details>`，裡面就是現有的 `RosterView`（篩選、排序、小卡不改）。
- **抽屜焦點歸還**：同一名球員會有多顆名牌按鈕共用 `data-open-player`，現有 `querySelector` 只會回到第一顆。要改成記住實際觸發的元素並把焦點還給它，PRD 要求焦點回原觸發處。
- `roster_status !== "submitted"`：該隊欄顯示「待更新」。`series_pending_games` 照現行規則顯示「待更新」標記。`series_unknown`／`null` 的分支不改。

**`web/src/components/playoffs/playoffs-live.tsx`**

- 預期**不需改**：掛點經 `area-registry` 掛 `RosterSection`，介面不變。真的要動時只限掛點。

**測試**

- 專案前端測試是 `npm test`，也就是 `node --test` 加 `react-dom/server` 靜態渲染，**不是 vitest**（派工寫 vitest，這裡更正）。
- 測試放在既有的 `roster-section.test.tsx`、`playoffs-roster.test.ts`。

### 4.2 測試補強（每項對應驗收或風險）

| # | 測試 | 支持 |
|---|---|---|
| T1 | `RosterCompare` 靜態渲染：兩隊欄同時存在（例如 `[data-compare-team]` ×2），不需要任何互動 | 驗收 1（兩隊對照）的機械前提 |
| T2 | `positionCounts` 與組成列文字和 fixture 一致 | 驗收 1（投／野各幾人） |
| T3 | `roleRows`：已知序、未知角色接尾、兩隊皆空的列省略、多角色球員出現在各所屬列、同列依 scopeG 降冪、series scope 用本系列 G、pending 顯示「待更新」而不是 0G | 驗收 1、3；風險：#349 角色資料變動 |
| T4 | 一隊 `roster_status=missing`：該欄「待更新」，另一隊照常 | 驗收 3（缺資料看得出來） |
| T5 | 名牌按鈕有 `aria-haspopup="dialog"`；同一球員多顆名牌時焦點回到被點的那顆（純函式或 DOM 測） | 已列風險：抽屜回焦退化 |
| T6 | 既有小卡、篩選、排序、頁尾說明測試全部保留並照常通過（明細內容不變） | 回歸：明細區沿用現有行為 |

### 4.3 驗收取證（正式站，執行完成並經授權部署後）

**取證步驟**：真實瀏覽器，以 https://cpbl.ruan-ruan.com/ 的導覽列「季後賽」**一般點擊進入** → 點頁籤「系列賽名單」→ 截圖 → **重新載入** → 再進入頁籤截圖。桌機 1280 寬與 390 寬各一組。

**各驗收的證據**

- **驗收 1**：需求方本人在正式站看（人工審核，見 §5）。
  - 輔助證據：截圖，加上 DOM 量測，證明兩隊欄同時可見、`scrollWidth ≤ 視窗寬`。
- **驗收 2**：上面四張截圖，加上截圖時的 `last_refresh_at`。CI 與本機截圖不能取代。
- **驗收 3**：
  - `git diff --name-only <基準>..HEAD` 只有 `web/` 檔，沒有 `src/`、`migrations/`。
  - 正式站 API 回應的 `roster_version`／`revision_hash` 與畫面所用的版本相同。
  - 畫面角色與 API `tactical_roles` 逐列抽三人比對。#349 合併後要以新資料再比對一次。

## 5. 影響範圍、分工、風險、回復、停止條件

**影響範圍**

- 只影響 `/playoffs` 第 3 區前端呈現。
- 不影響第 1、2、4 區、抽屜內容、API、DB、排程與主站介接（`/api/info`）。

**相依與並行**

- #349 改的是角色資料。#349 PM 預期不動本卡三檔，但**未經其規劃確認**。
- 開工時執行者先在當下 `origin/main` 確認 #349 的 diff 沒有碰這三檔；有碰就停下回報 PM。
- 合併順序預設 #349 先，本卡 rebase 到其後的 main。

**分工**

- 執行者：獨立的 Claude 工作階段，使用新 worktree。
- 審核者：依 PM 安排，用不同模型家族（卡上規劃為 Codex）。
- 部署：需求方另行授權，在主站 bump submodule。

**人工審核需求**

- 需求方用桌機瀏覽器（約 1280 寬）和手機（約 390 寬）開正式站 `/playoffs` → 「系列賽名單」。
- 判定標準是「不讀說明，能說出兩隊投／野人數、各角色是誰、誰是主力」。

**風險**

1. #349 合併後角色分布改變，可能新增角色。對策：列表依資料產生、未知角色接尾（T3）。
2. 多角色重複出現讓野手段變長，屬設計取捨，由需求方看 mockup 判斷。
3. 抽屜回焦退化（T5）。
4. 明細收合後，習慣舊版的使用者找不到箭頭與 PR。由需求方決定是否接受（§3 衝突 2）。

**回復方式**
