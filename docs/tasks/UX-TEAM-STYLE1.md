## 背景（為什麼）

TEAM-STYLE1 建立了七個可解釋的隊季風格軸（季內聯盟 z-score）並驗出各軸的穩定性剖面；
TEAM-STYLE2 檢定「教練任期分段」假說為 No-Go。球隊頁據此新增「球風」區塊，
把研究結論轉成訪客看得懂的呈現——**研究已畫好「事實」與「標籤」的界線，本卡的任務
是忠實呈現這條界線，不是重新發明**。

## 設計約束（研究定案＋需求方裁定，不得於實作中放寬）

1. **本季 vs 聯盟比較優先**（需求方 2026-07-27 裁定）：主呈現＝七軸雷達（z 值）＋
   每軸 tooltip／明細給**原始數值與聯盟排名**（例「短打 38 次，聯盟第 1」）。
   一般球迷看次數與排名，進階使用者看 z。
2. **分段維持逐季**（STYLE2 No-Go）：歷史檢視以季為單位；教練名**只作時間標記**
   （如年份軸上標示「陳金鋒 2024–」），不得以任何文案暗示「某教練時期有一致風格」。
3. **軸級語意標注**（STYLE1 穩定性剖面，逐軸固定）：
   - 選球紀律：唯一可標「**具跨季延續性**」的軸
   - 速度戰／短打戰術／長打火力：可用，標注其穩定性語意（短打／長打季內偏噪）
   - 先發吃局／三振型投手：**必標「本季」**——季內成立、跨季不延續
   - 守備效率：**只放數字不放形容詞**——不得出現任何風格標籤或傾向描述
4. **不做球隊層級的持久標籤**（v1）：「○○是選球紀律型球隊」這類跨季身分宣稱需要
   另定規則（哪隊夠格、幾季門檻），v1 不做；只做上述**軸級**語意標注。
5. **零預測性語言**：不得出現「因此勝率／戰績…」等連結賽果的文案。
6. **計算單一來源**：軸計算式抽成 `src/cpbl/` 共用模組（研究腳本與 API 同源），
   定義以 TEAM-STYLE1 凍結 spec（`50c23be`）為準，**不得重算、變造或另创口徑**；
   共用化後研究腳本重跑 artifact 須逐位不變（除時間戳）作為重構等價性證據。
7. **口徑**：全季（season-level z）；**不接**球隊頁既有的半季 ContextSwitcher
   （軸定義是季內 z，半季樣本噪音大，STYLE1 分半檢定已證）；區塊內明示「全年」。
8. 2026 進行中賽季照算照顯（消費表面本來就要本季），但歷史比較圖中對進行中賽季
   標注「賽季進行中」。

## 範圍

- **API**：新端點（`/api/v1/season/team-style` 一類，路由快照同步加 EXPECTED）回傳
  指定隊季的七軸 z＋raw＋聯盟排名＋軸級語意標注；唯讀、request-time 由 gamelog/games
  聚合（沿站內 derived-stats-computed-live 慣例），聯盟彙總僅 4–6 隊成本可忽略。
- **前端**：球隊頁新增「球風」區塊——雷達（走 useChartTheme）＋軸明細（raw＋排名＋
  語意標注）＋歷史逐季檢視（含教練時間標記）。設計系統遵循 `docs/design/UI_UX_SYSTEM.md`。
- **共用模組抽取**：`scripts/team_style_vectors.py` 的軸計算抽至 `src/cpbl/`，
  腳本與 API 共用。
