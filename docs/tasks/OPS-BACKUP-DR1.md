## 問題陳述

`OPS-BACKUP-EMPTY1` 修好的是「備份會不會產出、內容夠不夠」——它讓 88 天的空檔缺陷不再可能，
`backup-prod-db.sh` 現在會驗 `CREATE TABLE` 數與位元組數，未達門檻即 `exit=66`。

**但它沒有動兩件事，而那兩件才是「災難真的發生時能不能救回來」的部分。**

**一、備份的故障域可能只有一個。** 現存三份整庫備份都在 `/opt/backups`（VPS）。
若 VPS 本身損毀、被刪、或帳號失去存取，備份與被備份的資料**一起消失**。
異地副本目前不存在——需先由 Discovery 量出現行拓撲，再談要不要補。

**二、還原演練只做過一次，而且是人工的。** 那一次演練是本專案唯一一次真的把備份還原回去，
結果**抓到了只有還原才看得見的問題**：`FK=15` vs 修復前的 `13`——`convalidated=t` 卻實際
不成立的外鍵，會讓 `ON_ERROR_STOP=1` 在外鍵階段中止。這件事**沒有任何自動化在守**，
下一次備份格式、schema 或 PG 版本變動導致還原失敗時，不會有人知道，直到真的需要還原。

### 這張卡要對抗的是同一個病

`OPS-BACKUP-EMPTY1` 留下的教訓是「**失敗會留下看起來像成功的產物**」——那 86 份 20-byte 空檔
每一份都通過 `gzip -t`。本卡是這句話的下一層：**「備份檔存在且內容夠大」仍然只是一個看得見的
標記，「這份備份還原得回一個可用的資料庫」才是該成立的性質。** 兩者之間隔著 schema 相容性、
外鍵有效性、擴充套件、PG 版本與還原順序——全都只有真的還原一次才驗得到。

## 非目標

- **不改 `backup-prod-db.sh` 既有的內容門檻邏輯。** 它已由變異檢驗證明有效（連線失敗 `exit=23`、
  空 dump `exit=66`），本卡在其外面加層，不重寫它。
- **不做多版本保留策略的大改**（保留幾份、輪替規則），除非 Discovery 證明異地方案本身逼出這個決定。
- **不新增 VPS 上的常駐服務。** 爬取與備份的執行面在開發機，維持現狀。
- 不處理主站 `public` schema 以外的其他資料（本備份已涵蓋整庫 99 表 ＝ cpbl 81 ＋ public 18）。

## Discovery 必答（先答再改碼）

1. **現行備份實際存在哪幾個位置、各自的故障域是什麼？** 要列出實際路徑與產生者
   （VPS `/opt/backups` 由誰寫、開發機是否留有副本、`refresh-cpbl-prod.sh:116` 取得的
   `BACKUP_PATH` 最終落在哪）。**「單點」要用實際盤點證明，不得假設。**
2. **異地目標選什麼？** 至少評估「開發機本地保留」「物件儲存（S3／B2／R2）」「另一台主機 rsync」
   三類，判準依 Solopreneur-first：**低維護成本與自動化難易優先於功能豐富**。須回答經常性成本、
   憑證放哪（不得進 repo）、是否需要加密、以及**還原時取回的實際步驟有幾步**。
3. **還原演練自動化到什麼程度？** 全自動排程演練 vs 一鍵可重跑的半自動。要回答：演練在哪跑
   （拋棄式 PG17 容器的資源需求）、多久一次才有意義、以及**失敗時告警送到哪**——
   本專案目前**沒有任何告警管道**，若答案是「寫進 log」等於沒有守衛（見紅線 2）。
4. **演練要驗到什麼深度才算數？** 至少要能重現結案時那次演練抓到的問題類型
   （外鍵有效性）。表數／列數／FK 數之外還需要什麼斷言，要用**性質**描述而非列舉當時的數字。

## 驗收條件

- [ ] 備份**至少存在於兩個獨立故障域**，且「獨立」的判準在 Discovery 中明確定義並可查證；
      任一故障域整體不可用時，剩餘副本仍足以還原出完整資料庫。
- [ ] 還原演練**可重複執行且不依賴人工判讀**：演練程式自行斷言還原結果是否可用，
      失敗時以非零 exit code 結束並產生可讀的失敗原因；**不得以「有產出報告」代替「有驗證結論」**。
- [ ] 演練斷言涵蓋的性質必須包含外鍵有效性——即能偵測「`convalidated=t` 但實際不成立」這類
      只在還原時才暴露的問題；斷言以性質表述，不得硬編當次的數值。
- [ ] 演練失敗**必然被察覺**：告警送達一個需求方實際會看到的管道，且該管道本身經過一次
      故意觸發的驗證。若 Discovery 結論是不建置告警，須明確說明「失敗時如何被發現」，
      不得留白。
- [ ] 異地推送與演練**不得干擾既有每日鏈**：失敗不阻斷 `refresh-cpbl-prod.sh`，
      不改變既有備份的產生時點與內容門檻行為。
- [ ] 憑證與存取金鑰不進 repo、不寫入 event log 或卡面；取得方式以環境變數或本機設定檔記載。

## 紅線（違反即退回）

1. **不得以檔案存在、大小或 `gzip -t` 作為演練通過的判準。** 這正是本卡上游缺陷的失敗模式——
   必須真的還原出可查詢的資料庫並對其斷言。〔驗證深度〕
2. **不得宣稱建立了守衛卻無人會看到它的失敗。** 只寫進 log 而無人閱讀的告警等同沒有守衛；
   若不建告警，須在卡面明寫「失敗如何被發現」的替代機制。〔守衛有效性〕
3. **演練全程不得連線 production DB 進行寫入，也不得覆寫任何既有備份。** 還原目標一律為
   拋棄式容器。〔生產安全〕
4. 現存三份整庫備份（含 `/opt/backups/full-alpha_db-pre-RECALC1-20260731-075723.sql.gz`，
   240,274,215 bytes）**不得刪除或移動**，它們是 `INGEST-SPLITS-RECALC1` Phase P 的回滾依據。〔資料保全〕
