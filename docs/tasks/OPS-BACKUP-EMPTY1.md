## 問題陳述

生產 PostgreSQL 的每日 03:00 自動備份**從未產出過一份可用的備份**。

2026-07-29 實測（`/opt/backups`）：

- 共 **86 份** `backup_alpha_db_*.sql.gz`，**每一份都是 20 bytes**（gzip 對空輸入的長度），解壓後 **0 bytes**
- 以 `find -size +1k` 計數非空檔：**0 份**
- 檔名時間戳最舊 `20260505_030001`、最新 `20260729_030001` → **連續 86 天**

`/var/log/db-backup.log` 直接記下了原因，每天一行：

```
pg_dump: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL:  role "admin" does not exist
```

也就是說：**生產資料庫在至少 86 天內處於「沒有任何可用備份」的狀態**，而監控面看起來一切正常。

## 根因（已定位，非推測）

`infra/scripts/backup-db.sh` 三個因素疊加：

1. `DB_USER="${DB_USER:-admin}"` —— 預設值 `admin` 與生產實際使用者 `app_writer` 不符。
2. cron 直接呼叫腳本、**未 source `.env`**，所以 `DB_USER` 走預設值 → `pg_dump` 以不存在的 role 連線 → 失敗。
3. ~~腳本**缺 `set -o pipefail`**，退出碼取自 `gzip`（成功），於是 pg_dump 的失敗被吞掉，
   腳本繼續執行並印出「`==> 備份完成: ... (20)`」。~~
   **✗ 此點經 2026-07-29 實地查證為誤，見下方更正。**

> ### 更正（2026-07-29T14:40+08:00，Claude Opus 5@Claude Code 實地查證）
>
> **原第 3 點不成立。** `backup-db.sh` 第 2 行就是 `set -euo pipefail`，腳本每次都正確中止了。
> 生產 `/var/log/db-backup.log` 的決定性計數：**「開始備份」86 次、「備份完成」0 次、「清理舊備份」0 次**。
> 若失敗真被吞掉，86 次都該印出「備份完成」。
>
> 真正的缺陷是另外三個，原分析全數漏掉：
>
> 3a. **失敗仍留下空檔（假備份）**：`| gzip > "${FILEPATH}"` 的 shell 重導向在 pipeline 執行**之前**
>     就建立檔案，gzip 對空輸入寫出 20-byte header。腳本中止後空檔留在原地，
>     目錄看起來「每天都有備份」。**這才是「監控面看起來一切正常」的成因**——
>     不是退出碼被吞，是失敗留下了長得像成功的產物。
> 3b. **非零退出碼沒有接收者**：cron 為 `... >> /var/log/db-backup.log 2>&1`，無 `MAILTO`、無任何告警管道。
>     腳本確實回報了失敗，但 86 天沒有任何人或系統在接收。
> 3c. **`KEEP=30` 清理邏輯不可達**：清理段落位於 pipeline 之後，腳本早退所以從未執行。
>     這正是「86 份 > KEEP=30」的完整解釋（原紅線 2 列為「行為不明、待查明」，此處查明，
>     **保留邏輯本身沒有壞**）。
>
> 觸發原因 1、2 維持成立（`.env.example:23` 明寫「不要用 'admin'」，而 `backup-db.sh:15`
> 預設值正好是 `admin`，兩處獨立佐證）。
>
> **對修復方向的影響**：目標 1「加 `set -euo pipefail`、失敗時非零退出」是 no-op，
> 腳本本來就有、本來就會。真正要修的是 3a／3b——**先寫 `.part`、驗證通過才改名**，
> 以及**建立一條 log 以外的告警管道**。

## 為什麼優先

這與 `DEV-VERIFY-TM-ASSERTS1` 是**同一型缺陷**：把「腳本沒丟例外」當成「該成立的性質成立」。
但本卡的後果更重——那一支是驗證腳本失效，這一支是**災難復原能力歸零而且無人知情**。

發現途徑本身值得記下：這是因為 `DATABASE_CONTRACT.md` 規定「結構操作前必先備份」、
且 `AI_RUNBOOK.md` 規定「看見『已驗證備份』前不得進 production migration」，
執行者去查備份時才發現。**紅線救了一次場**——但也說明目前沒有任何主動告警會發現它。

## 目標

1. ~~修 `backup-db.sh`：`set -euo pipefail`、明確取得正確憑證、**失敗時非零退出**。~~
   **改為**：失敗時**不得留下產物**——先寫 `"${FILEPATH}.part"`，通過驗證才 `mv` 成正式檔名。
   （`set -euo pipefail` 與非零退出**已經存在且已在運作**，見上方更正；本項唯一要修的是
   「shell 重導向先建檔」導致的假備份。）另修正憑證：cron 需 source `.env`，或腳本改為
   讀不到 `DB_USER` 就**中止而非套用 `admin` 預設值**（預設值本身就是陷阱）。
2. 加**產出驗證**：備份完成後檢查 `gunzip -t` 通過且解壓後大小／表數超過門檻，否則視為失敗。
3. 加**告警**：失敗要有人知道。形式由執行者提案（cron MAILTO、寫入主站健康端點、
   或現有 `/api/info` 之外的獨立管道）——**只寫 log 不算**，這次就是 log 有寫但沒人看。
4. 補上目前缺的**還原演練**：證明產出的備份真的能還原，不只是「檔案不是空的」。

## 紅線

1. **不得對生產執行還原**。還原演練只能對本機或拋棄式實例。
2. **不得刪除現有 86 份空檔**，直到查核者確認過曝險範圍——它們是本卡的證據。
   （~~另注意：腳本寫 `KEEP=30` 但實際留了 86 份，**保留邏輯顯然也沒在運作**，一併查明~~
   → **已查明（2026-07-29）**：保留邏輯沒有壞，只是位於 pipeline 之後、腳本早退所以從未執行；
   log 中「清理舊備份」出現 0 次。修好前置後它會自然生效——**修復後首次成功執行會一次刪掉
   56 份空檔**，而紅線 2 要求保留它們作為證據，故執行者需在修復期間先把空檔移出
   `KEEP` 的匹配範圍或另存，勿讓清理邏輯毀證。）
3. 修好之後**必須做變異檢驗**：故意讓 pg_dump 失敗（例如給錯 role），證明腳本**非零退出**且告警觸發；
   正常情況照樣通過。沒有變異檢驗的修復不算數。
4. 本卡不改資料，只改腳本與排程。
