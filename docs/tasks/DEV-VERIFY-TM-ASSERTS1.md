## 問題陳述

該腳本跑完會印 `ALL VERIFICATIONS COMPLETED SUCCESSFULLY!`，但四段裡只有最後一段有真的比對：

1. 本地／生產覆蓋率比對 —— 兩邊各 `logger.info` 印出來，**無 assert**
2. 隨機完成場逐列抽驗 —— 兩邊各印前 10 列，**無 assert**
3. 非目標欄位完整性 —— 只印生產端統計，**無 assert**
4. 生產 API 健康檢查 —— `assert req.status == 200`、`assert info.get("status") in (...)`

也就是說：**local 與 prod 的資料完全兜不起來，腳本一樣正常 exit 0 並宣告成功。**
而且不需要特殊環境觸發，每次執行都這樣。

這是「**檢查腳本沒丟例外**」當成「**資料真的一致**」——把一個看得見的標記，
當成該成立的性質。2026-07-29 `DEV-TRAILER-GUARD-SCOPE1` 的盤點在同一天內找到第五個同型案例，
但這一個的風險最高：前四個是守衛在某些環境靜默失效，**這一個是任何環境下都沒在驗**。

## 為什麼要修

這支腳本的用途是「深度 TrackMan 回填之後，確認生產資料與本地一致」。
它現在提供的是**一份並排的資料傾印**，需要人眼去比——而它印出的成功訊息會讓人以為機器已經比過了。
**比沒有腳本更危險**：沒有腳本時人知道要自己看，有腳本時人以為已經驗過。

## 目標

前三段補上真正的比對。**判準要多嚴格是設計決策，需執行者提案**，例如：

- 覆蓋率：完全相等？允許生產落後本地一定筆數（同步時間差）？
- 逐列抽驗：欄位逐一相等？浮點欄位（`real`）要不要容差——本專案曾在 `real(float4)` 對帳踩過雷（見 `INGEST-GAME-TM-REFACTOR1` 記錄）？
- 非目標欄位：要跟什麼比？目前只印生產端，沒有基準。

**先提案再實作**：把每一段「該成立的性質是什麼」寫清楚，再決定斷言形式。

## 紅線

1. **不得把「印出來」當成「驗過了」**。任何一段若最後決定不做機器比對，
   成功訊息**必須明確排除該段**，不得由一句 `ALL VERIFICATIONS COMPLETED SUCCESSFULLY!` 概括。
2. **變異檢驗必做**：構造 local 與 prod 不一致的情境，證明腳本會**非零退出**；
   一致時正常通過。沒有變異檢驗的斷言不算數。
3. 浮點比對若採容差，容差值與理由要寫在程式碼裡，不得憑感覺選。
4. 本卡**唯讀**：不得為了讓比對通過而修改任何資料。
